# Architecture Decisions

This document tracks all architecture and technology decisions made for this project.

## 2026-03-21: Initial stack audit and modernization

### AD-001: Replace webrtcvad with silero-vad-lite
- **Context**: webrtcvad is unmaintained, only 50% true-positive rate
- **Decision**: Use silero-vad-lite (87.7% TPR, zero heavy deps, 16kHz native)
- **Trade-off**: API change (boolean -> float probability), 32ms frames instead of 30ms

### AD-002: Pin aioesphomeapi >= 44.0.0 and aiohttp >= 3.13.3
- **Context**: aioesphomeapi was pinned at >=21.0.0 (24 major versions behind). aiohttp had 8 CVEs (Jan 2026)
- **Decision**: Bump both to current secure versions
- **Trade-off**: Requires Python >= 3.11

### AD-003: Clean requirements.txt
- **Context**: 7 of 12 dependencies were unused (fastapi, uvicorn, websockets, asyncio-mqtt, pydantic, aiofiles, python-multipart). numpy was used but missing.
- **Decision**: Remove unused deps, add numpy

### AD-004: Extract hardcoded config to environment variables
- **Context**: ESP IP, port, password, LLM URL were hardcoded
- **Decision**: Use env vars (ESP_HOST, ESP_PORT, ESP_PASSWORD, ESP_NOISE_PSK, LLAMA_URL, HTTP_PORT) with sensible defaults
- **Trade-off**: None, strictly better

### AD-005: Support noise_psk encryption
- **Context**: ESPHome 2026.1.0 removed password auth. Current ESP runs 2025.6.2 so not urgent, but preparing for the upgrade.
- **Decision**: Support ESP_NOISE_PSK env var, fallback to ESP_PASSWORD

## 2026-03-21: Split STT/LLM pipeline

### AD-006: Replace combined Voxtral STT+LLM with separate Parakeet STT + text LLM
- **Context**: Voxtral Mini 3B via llama.cpp had poor French support (responded in English), no transcript visibility, and audio support in llama.cpp is "highly experimental"
- **Decision**: Split into Parakeet MLX for STT + text-only LLM via llama.cpp
- **Trade-off**: Two models to load instead of one, but each is best-in-class for its task

### AD-007: Use Parakeet TDT 0.6B v3 (via parakeet-mlx) for STT
- **Context**: Compared Whisper Large V3 Turbo vs Parakeet V3. Parakeet wins on French accuracy (6.3% vs 7.4% WER), speed (~0.7s vs 3-5s), RAM (~2GB vs 3-6GB), and zero hallucinations.
- **Decision**: parakeet-mlx with mlx-community/parakeet-tdt-0.6b-v3
- **Trade-off**: Only 25 European languages (vs Whisper's 99+), but French is all we need

### AD-008: Use SmolLM3 3B for text LLM (instead of Qwen 3 8B)
- **Context**: Qwen 3 8B had great tool calling (F1: 0.933) but was slow on M1 (12.8 tok/s, ~6s total). SmolLM3 3B is 2.3x faster (29.5 tok/s, ~1.1s total) with French as a first-class language.
- **Decision**: SmolLM3 3B Q4_K_M via llama.cpp
- **Trade-off**: Less capable for complex reasoning, but for home automation commands this is more than enough. Can always switch back to Qwen 3 8B if needed.

### AD-009: Use /no_think to disable Qwen 3 reasoning mode
- **Context**: Qwen 3 8B defaults to "thinking" mode, putting all output in reasoning_content and returning empty content. This adds latency and wastes tokens for a voice assistant.
- **Decision**: Prefix system prompt with /no_think. Also handle <think> tags in response parsing as fallback.
- **Note**: This decision applies if we switch back to Qwen 3. SmolLM3 does not have this issue.

### AD-010: All code and comments in English
- **Context**: Original code had French comments and docstrings
- **Decision**: English for all code artifacts. User-facing LLM system prompts stay in French (the assistant responds in French to the end user).

### AD-011: Replace Piper TTS with Kokoro-82M (kokoro-onnx) + misaki French G2P
- **Context**: Piper TTS (fr_FR-gilles-low) had poor French accent quality ("québécois et bizarre"). Kokoro-82M has a French voice (ff_siwis) with significantly better pronunciation when paired with explicit French phonemization via misaki/espeak.
- **Decision**: Use kokoro-onnx with misaki EspeakG2P(language='fr-fr') for French phonemization. Resample 24kHz output to 16kHz for ESP compatibility.
- **Trade-off**: Kokoro outputs at 24kHz (requires resampling to 16kHz for ESP). Only 1 French voice available (ff_siwis). Model is larger (~310MB vs ~30MB for Piper). Requires espeak-ng system dependency.

## 2026-03-21: Home Assistant integration

### AD-012: Control Home Assistant via REST API with 6 generic LLM tools
- **Context**: The voice assistant needs to control real home automation devices. User has a local Home Assistant installation.
- **Decision**: Connect to HA REST API (local, no cloud) with a long-lived access token. Expose 6 generic tools to the LLM: turn_on, turn_off, open_cover, close_cover, set_temperature, get_state. Entity resolution uses fuzzy matching on friendly_name (the LLM says "lumière salon", Python matches it to `light.salon`).
- **Trade-off**: 6 tools is the max a small model can handle reliably. No second LLM round-trip after tool execution (function result goes directly to TTS for lower latency). Entity list injected into system prompt for context.

### AD-013: Switch from SmolLM3 3B to Qwen 3 4B for LLM
- **Context**: SmolLM3 3B does not support function/tool calling — it returns text responses instead of tool_calls JSON. Qwen 3 4B has native tool calling support (trained with function calling in its chat template).
- **Decision**: Use Qwen 3 4B Q4_K_M via llama.cpp with --jinja flag. Keep /no_think prefix to disable reasoning mode.
- **Trade-off**: Slightly slower than SmolLM3 (~5s cold, ~1.5s warm vs ~1.3s), but tool calling actually works. Still fits in 16GB RAM alongside Parakeet STT and Kokoro TTS.
- **Note**: Qwen 3 4B requires thinking mode (no `/no_think`) for reliable tool calling. With `/no_think` it outputs tool calls as plain text instead of structured `tool_calls`. Thinking mode adds ~5s latency but is the only way to get reliable function calling.

### AD-014: Entity resolution using HA areas and room parameter
- **Context**: Entities in different rooms can have the same name (e.g., "Plafonnier" in Chambre Charlie and Chambre invités). Flat entity lists caused the LLM to pick the wrong one.
- **Decision**: Fetch HA areas via template API, group entities by room in the system prompt, add `room` parameter to all LLM tools. Entity resolution scopes by room first, falls back to global search.
- **Trade-off**: More template API calls at startup (~1 per area). Slightly larger prompt but better structured for the LLM.

### AD-015: Room groups for multi-room commands
- **Context**: User wants to say "ferme les volets des enfants" or "éteins toutes les lumières" and have it affect multiple rooms.
- **Decision**: Define ROOM_GROUPS in ha_client.py (e.g., "enfants" → [Chambre Zoé, Chambre Charlie], "tout/partout" → all rooms). When a room group is detected, return ALL entities of the target domain across all rooms in the group. LLM passes the group name as the room parameter.
- **Trade-off**: Server-side compensation for the small LLM's inability to reliably make multiple tool calls. Groups are hardcoded (not dynamic from HA).
- **Update 2026-10-10**: « tout », « toute la maison » and « partout » are built in; `config.local.json` keeps only real subsets like « enfants » (entries for those three words in an older file are dropped at load). A room list cannot reach a device HA has in no room: in Paris, « lumières partout » found 12 lights with the old list and finds 15 now, with Entrée, Bibliothèque and Couloir. A generic name (« les lumières ») takes every device of its kind, in a room or not; a sweep over several domains (« éteins tout ») keeps to devices in a room, which leaves alone the loudness and cross-fade switches of the Paris Sonos, itself in no room. Also, a generic name now keeps a group to its own domain: « éteins les lumières des enfants » (turn_off hints light, switch and media_player) used to switch off every switch and speaker in those rooms too.

### AD-016: Stay on Qwen 3 4B Q4_K_M (benchmarked vs 8B)
- **Context**: Benchmarked Qwen 3 8B Q4_K_M on M1 16GB. Warm latency: 3.1s (vs 1.7s for 4B). RAM: ~5GB (vs ~950MB). Tool calling works with both thanks to Python compensation.
- **Decision**: Stay on 4B for lower latency. Revisit if tool calling reliability becomes an issue or if a better model becomes available.
- **Trade-off**: Less capable for complex reasoning, but acceptable for home automation commands.

### AD-017: Conversation history for multi-turn context
- **Context**: Each LLM call was stateless — no memory between turns. Impossible to say "allume la lumière du salon" then "éteins-la".
- **Decision**: Keep last 5 exchanges in memory, expire after 2 min of inactivity. Add French action verb fallback parser for when local LLM responds with text instead of tool calls.
- **Trade-off**: More tokens per request (~200 extra for history). Fallback parser is a workaround for small local models — unnecessary with cloud APIs.

### AD-018: Cloud LLM API support (GPT-5.4 Nano)
- **Context**: Local Qwen 3 4B struggles with multi-turn tool calling (responds with text instead of structured tool_calls). Tested GPT-5.4 Nano via OpenAI API as interim solution.
- **Decision**: Support both local (llama.cpp) and cloud (OpenAI-compatible API) via env vars LLM_URL, LLM_API_KEY, LLM_MODEL. GPT-5.4 Nano: reliable tool calls, pronoun resolution, ~1.3s latency, ~$0.39/month.
- **Trade-off**: Introduces cloud dependency (breaks 100% local goal), but temporary until dedicated hardware (Zotac + 14B local model). Local mode remains the default.

## 2026-03-22: Service management, refactoring, weather

### AD-019: macOS Keychain for secrets
- **Context**: HA token stored in env vars was lost on context compaction. User had to regenerate tokens.
- **Decision**: Store secrets in macOS Keychain (`voice-assistant-ha-token`, `voice-assistant-openai-key`). `run.sh` reads them at launch and exports as env vars. Voice server only reads env vars.
- **Trade-off**: macOS-specific. Secrets survive context compaction and system restarts.

### AD-020: launchd service management with signal-based control
- **Context**: No standardized way to start/stop/restart/reload the server.
- **Decision**: Use launchd plist (`com.voice-assistant.server.plist`) for daemon management. `ctl.sh` wraps launchctl commands. SIGHUP triggers hot-reload of HA entities. SIGTERM triggers graceful shutdown. `run.sh` uses `exec` so signals reach Python directly.
- **Trade-off**: macOS-specific (launchd vs systemd). `ctl.sh` polls log markers instead of sleeping for ready detection.

### AD-021: Refactoring into modules
- **Context**: `voice_server.py` grew to 1315 lines — hard to navigate and maintain.
- **Decision**: Extract into 6 modules: `stt.py`, `tts.py`, `llm.py`, `ha_client.py`, `weather.py`, `web_ui.py`. `voice_server.py` remains the orchestrator (~660 lines).
- **Trade-off**: More files, but each module has a clear responsibility and can be understood in isolation.

### AD-022: Web UI for debugging and text input
- **Context**: No way to visualize exchanges or test without the ESP hardware.
- **Decision**: Web UI at `:8888` with exchange log, debug panel (timings, tool calls), and text input. OS-adaptive light/dark theme via `prefers-color-scheme`. Exchange log persisted to `exchanges.json` to survive restarts.
- **Trade-off**: Adds ~280 lines to `web_ui.py`. JSON persistence is simple but not concurrent-safe (acceptable for single-user).

### AD-023: Weather tool via Open-Meteo
- **Context**: User wants to ask the assistant about weather. Needs to work without API keys (100% local goal).
- **Decision**: Use Open-Meteo API (free, no key). Default to Paris 15e. Geocoding for other cities. Returns structured JSON with current conditions + 5-day forecast. WMO codes mapped to French descriptions.
- **Trade-off**: Requires internet (not truly local), but no API key or account needed. Open-Meteo has generous rate limits.

### AD-024: Second LLM round-trip for natural tool responses
- **Context**: Raw tool results (e.g., weather JSON, "Plafonnier éteint") went directly to TTS — sounded robotic and unnatural.
- **Decision**: After tool execution, send results back to LLM for natural language formulation. The LLM receives tool results and generates a spoken response.
- **Trade-off**: Adds ~0.5-1s latency per response. Worth it for much better TTS output quality.

### AD-025: Multi-round tool loop
- **Context**: GPT-5.4 Nano doesn't always emit all needed tool calls in one shot (e.g., "éteins la lumière et dis-moi la météo" only called turn_off).
- **Decision**: After tool execution, send results back with tools still available (up to 3 rounds). Add system reminder listing already-called functions to nudge the model to handle remaining parts of the request.
- **Trade-off**: Up to 3 LLM round-trips per user query. In practice, 2 rounds handle 99% of cases. Adds ~1s for multi-part requests.

### AD-026: Continuous conversation via announcement API
- **Context**: User had to say the wake word between every turn, breaking conversational flow.
- **Decision**: After TTS generation, deliver audio via `send_voice_assistant_announcement_await_response(start_conversation=True)` instead of event-based TTS_END. The ESP automatically starts a new pipeline without wake word. 500ms audio skip at follow-up start to avoid TTS echo pickup. 5s timeout for follow-up silence (extends to 30s once speech detected). `end_conversation` LLM tool for clean closure ("merci", "bonne nuit") — skips follow-up and clears history.
- **Trade-off**: Slightly more complex pipeline flow. The announcement API replaces event-based TTS delivery. ESP stays in active mode between turns (LEDs on, mic open).

### AD-027: Server-side timer manager with ESP native timer events
- **Context**: User wants timers ("mets un timer de 5 minutes") and alarms ("réveille-moi à 7h"). ESPHome supports timers natively via `send_voice_assistant_timer_event()` (feature flag `VoiceAssistantFeature.TIMERS`), handling LED animations and sounds on the device.
- **Decision**: Server-side `TimerManager` in `timer.py` using asyncio tasks. Three LLM tools: `set_timer` (duration), `set_alarm` (absolute time), `cancel_timer`. Timer lifecycle sends events to ESP: STARTED, UPDATED (tick every 1s), CANCELLED, FINISHED. On FINISHED, additionally play a TTS announcement via the announcement API with `start_conversation=True` for follow-up.
- **Trade-off**: Timers are in-memory only — lost on server restart. Acceptable for kitchen timers; persistent alarms would need disk storage. The 1s tick loop is lightweight but adds continuous traffic to the ESP while timers are active.

### AD-028: Partial cover position support
- **Context**: Users want to say "ouvre les volets à 50%" instead of just fully open/close.
- **Decision**: Add `set_cover_position` tool with a `position` parameter (0-100). Update `ha_client.py` to call `cover.set_cover_position` and report the position in state descriptions when partially open/closed.
- **Trade-off**: One more tool for the LLM to handle. Stays within budget since it's in the same domain as open/close.

### AD-029: Automatic ESP reconnection with ReconnectLogic
- **Context**: Server blocked on startup if ESP was unavailable, and crashed on disconnect with no recovery.
- **Decision**: Use aioesphomeapi's `ReconnectLogic` for automatic reconnection with exponential backoff. Server starts even if ESP is offline and connects when available.
- **Trade-off**: Slightly more complex connection lifecycle, but eliminates manual restart on transient network issues.

### AD-030: Dynamic plist generation and .env for configuration
- **Context**: `com.voice-assistant.server.plist` contained hardcoded home directory paths. ESP/HA IP addresses were hardcoded as defaults in `voice_server.py`. Both problematic for public repo.
- **Decision**: Generate plist dynamically in `ctl.sh install` using `$SCRIPT_DIR`. Move IP/port config to `.env` file (gitignored), sourced by `run.sh`. Secrets remain in macOS Keychain.
- **Trade-off**: Requires `./ctl.sh install` on first setup instead of just copying the plist.

## 2026-03-23: Google Calendar integration

### AD-031: Google Calendar via OAuth 2.0 with granular scope
- **Context**: Google Calendar API requires OAuth 2.0 for personal accounts. Multiple scopes available from full access (`calendar`) to narrow event-level access (`calendar.events`).
- **Decision**: Use `calendar.events` scope (read+write events only). One-time OAuth setup via `setup_calendar.py` (requires browser). Refresh token handles automatic renewal. Token stored in `token.json` (file-based, gitignored) — standard approach for google-auth-oauthlib.
- **Trade-off**: File-based token is less secure than Keychain, but it's what Google's Python libraries use natively. Acceptable for a personal home server.

### AD-032: Single primary calendar for v1
- **Context**: Roadmap mentions multi-calendar with voice identification, but voice ID is not yet implemented.
- **Decision**: v1 uses only the `primary` calendar. Multi-calendar support will come with voice identification.
- **Trade-off**: Only one person's calendar is accessible for now.

### AD-033: No calendar injection in system prompt
- **Context**: Initially planned to inject a calendar summary into the system prompt. Testing showed GPT-5.4 Nano systematically calls the `query_calendar` tool regardless, making the injected summary redundant.
- **Decision**: No prompt injection. The LLM calls `query_calendar` on demand, which returns fresh data directly from the Google API.
- **Trade-off**: Every calendar question costs one tool round-trip (~1.5s), but the data is always fresh and the prompt stays lean.

## 2026-10-10: ESP on another site's network

### AD-034: `TTS_BASE_URL` overrides the announced TTS URL
- **Context**: Testing whether one GPU server (Charras) can serve an ESP at another site (Paris). The server connects out to the ESP, but the ESP downloads each reply WAV from the URL the server announces, built from the server's LAN address. Both sites use the same `192.168.1.0/24`, so that address names a different machine on the ESP's side, and no routing can tell the two apart.
- **Decision**: An optional `TTS_BASE_URL` env var replaces the computed URL, pointing at a relay on the ESP's LAN that forwards `/tts/` to the server. The native API needs no change: `ESP_HOST`/`ESP_PORT` already accept a forwarded port, and audio travels over that TCP connection (no UDP).
- **Trade-off**: One more setting, empty by default, so the single-LAN setup is unchanged. Rejected: site-to-site routing (impossible with overlapping subnets) and a second server instance per site (doubles STT/TTS VRAM beside the LLM).

## 2026-10-10: Web radio playback

### AD-035: Web radio playback, direct-to-ESP by default, HA fallback by room
- **Context**: User wants to play French web radios ("mets France Inter") with volume follow-ups ("plus fort", "moins fort"). The ESP32-S3 running `speaker.media_player` can decode MP3/FLAC/OPUS/WAV HTTP streams natively — no HA round-trip needed if the target is the ESP itself.
- **Decision**: Four tools — `play_radio(station, room)`, `stop_media(room)`, `set_volume(level, room)`, `change_volume(direction, room)`. Station names are fuzzy-resolved against a hardcoded `RADIO_STATIONS` dict in `voice_server.py` (18 French stations: Radio France family, RTL, Europe 1, NRJ, Skyrock, TSF Jazz, etc.).
  - Target resolution: `room` specified + matches an HA `media_player` entity → route via HA. Otherwise → the ESP that received the command, via `aioesphomeapi.APIClient.media_player_command()` (with `announcement=False` so the stream uses the default pipeline, not the TTS ducking pipeline).
  - The ESP's `media_player` entity key is discovered once in `on_connect` via `list_entities_services()` and cached in `device_media_keys[host]`.
  - `_last_media_target` (either `("esp", host)` or `("ha", entity_id)`) is remembered so "plus fort" after "mets france inter dans le salon" keeps targeting the right speaker.
  - Tools are registered unconditionally (present even if HA is offline), since ESP direct playback doesn't need HA.
  - After `play_radio`, `set_volume` or `change_volume`, the conversation ends (no follow-up listening): the open mic would otherwise pick the radio up and send it to STT as a request — from the ESP itself, or from a HA speaker that may share its room (the server has no way to know). Skipping follow-ups whenever something is playing would need the server to track media player states, which it does not do yet.
  - Station lookup returns nothing when a fuzzy match is ambiguous ("musique classique" hits two stations) or names no station ("la radio"), so the LLM asks instead of playing a random one.
- **Trade-off**: Hardcoded station URLs need manual updates when they move: by 2026-10-10, five of the first eighteen were already dead (France Bleu renamed ici, RMC, three NRJ-group streams) and were replaced after checking each returns `audio/mpeg`. The Voice PE decodes MP3, not AAC, so only MP3 streams are listed. Volume step for `change_volume` is whatever the ESP is configured for. A French fallback parser entry catches "plus fort"/"moins fort"/"monte le son"/"baisse le son" for local LLMs that emit text instead of structured tool calls.

### AD-036: No transcription when the VAD heard no speech
- **Context**: Parakeet hallucinates text on recordings where nobody spoke (a follow-up window that closed on silence, a wake-word request that hit the 30 s timeout), and the LLM answers it — once an apology for a request nobody made, right after the radio was stopped.
- **Decision**: `process_voice_pipeline` skips STT when the VAD never flagged speech in the recording, and takes the existing empty-transcript path (follow-up: end quietly; wake word: error LED).
- **Also**: no `STT_VAD_END` for such a recording. ESPHome 2025.6.2 handles `STT_VAD_END` by moving to `STOP_MICROPHONE` (then `AWAITING_RESPONSE` on its next loop) and ignores a `RUN_END` that arrives in `STOP_MICROPHONE`; with STT skipped, the `RUN_END` followed within a millisecond and the ESP stayed stuck "thinking", LEDs blinking. While the ESP is still `STREAMING_MICROPHONE`, `RUN_END` takes it back to idle.
- **Trade-off**: Speech too quiet for Silero VAD (threshold 0.5) is now dropped instead of transcribed; so far the VAD has caught every real request, and a hallucinated answer is worse than a red LED.
- **2026-10-13**: two requests in a row got the red LED, one plainly spoken (« Mercredi la semaine prochaine… »). The server kept one Silero instance for its lifetime, and Silero carries its state from window to window with no reset: replayed after the previous evening's request, the recording peaked at 0.26; through a fresh instance, 0.99. Each recording now gets a new instance (27 ms).
- **2026-11-20**: two requests at a tenth of the usual level, the satellite's microphone stuck low, got the red LED: speech that quiet after a wake word is amplified and heard (AD-113).

## 2026-10-10: Spotify

### AD-037: Spotify through go-librespot, streamed to the speakers like a radio
- **Context**: The family wants Spotify by voice ("mets du Daft Punk", "ma playlist du matin") on the Voice PE as well as on the Google Home / Sonos. The Voice PE is no Spotify Connect device. Spotify Connect through the Web API reaches Sonos, but a Google Cast device only shows up in the device list after a phone has woken it, so a voice command would often find no target. Music Assistant would cover every speaker, but it reaches the Voice PE only through HA, and the ESP accepts a single voice-assistant subscriber: with HA's ESPHome entry enabled, HA and this server would compete for it. The Paris HAOS VM also has 1 vCPU / 2 GB.
- **Decision**: go-librespot (a headless Spotify Connect player, separate systemd service on charras, configured in home-infra `charras/go-librespot`) writes raw PCM into a FIFO. `spotify.py` reads the FIFO at real-time pace (it writes as fast as it is read), pads the gaps (pause, track loading) with silence so that speakers never starve, encodes MP3 with ffmpeg while someone listens, and serves the stream at `/spotify/stream.mp3`, next to `/tts/` so that the Paris relay serves both. Any speaker plays that URL as it plays a radio: the ESP directly, an HA speaker through `media_player.play_media`.
  - Two tools: `play_music(query, kind, shuffle, room)` with kind in artist / track / album / playlist / liked, and `music_control(action)` for pause / resume / next / previous / current.
  - While music plays, the system prompt says what and on which speaker, so that "mets la musique sur la Google Home" moves it (`music_control` resume with a room, same position) instead of starting something else: without that line, gemma4:12b picked Liked Songs. With no room, media commands keep going to the last speaker used, which the family finds natural with a single Voice PE.
  - Playlists are looked up in the user's library first (go-librespot's `/library/playlists`, fuzzy on the spoken name), then in the catalog. Liked Songs is the `spotify:user:<username>:collection` context.
  - Catalog search uses a Spotify developer app of our own with the client-credentials flow (no user, no redirect). go-librespot's `/token` hands out its session token, but that token belongs to Spotify's desktop client ID, shared by every librespot install: on 2026-10-10 the Web API answered it with a standing 429 (Retry-After 30–60 s, renewed at each try).
  - The speaker is pointed at the stream first, and go-librespot starts once it has connected, so the first seconds are not lost. Starting the music on another speaker stops the previous one, if it is still on the stream. Music that plays to nobody for 5 s pauses go-librespot: that covers radio or stop on the Spotify speaker as well as a speaker stopped from elsewhere, with no Spotify case in the radio and stop paths. `music_control` acts on go-librespot's single queue without resolving a speaker.
  - At startup, the server picks up the HA speaker a previous run left on the stream or on a radio (`media_content_id` is the stream URL or a station's, state playing or paused) as the last media target, and as the Spotify speaker for the stream. Without it, a restart (a deploy) made media commands with no room go to the Voice PE while the music went on on the Sonos: on 2026-10-10 a `play_music` from a garbled request started a second copy of the stream on the Voice PE itself.
- **Measured**: ESP connected to the stream 130 ms after the command (through the Paris relay), Paris Google Home 1.3 s, playing after ~8 s of Cast buffering; Paris Sonos Roam SL plays it ~5 s after the command (it opens the URL twice first). go-librespot's position advances at exactly real time. 192 kbps MP3, 24 kB/s per listener.
- **Trade-off**: One go-librespot is one queue: one music at a time, on one speaker. Pause and skip take effect after the speaker's buffer (a second on the ESP, several on Cast). Search depends on a developer app whose owner must stay Premium (Spotify rule since 2026-02). Music started from a phone onto "Assistant vocal" plays to nobody until a speaker is pointed at the stream (ROADMAP follow-up).

## 2026-10-10: Pictures on the screen

### AD-038: Web pictures cast to the Nest Hub, from Wikipedia then Openverse
- **Context**: Both sites have a Google Nest Hub Max (Paris names it « Google Home »). Its software is locked — secure boot, no root or Linux port — so the only way in is Google Cast, and Cast shows media URLs: video, audio, pictures. The family wants « montre-moi la tour Eiffel », « à quoi ressemble un okapi ? ».
- **Decision**: a `show_image(query)` tool. `images.py` finds a picture and checks with a HEAD that its URL answers with an image (and which type); the server casts that URL with `media_player.play_media` and the screen loads it straight from Wikimedia or Flickr.
  - **Wikipedia first**: the lead image of the top French Wikipedia hit, 1280 px (the screen is 1280×800), kept only when every word of the query is in the article's title — « coucher de soleil sur la mer » otherwise lands on a painting's article. **Openverse otherwise**: free-licence photos, mostly Flickr at ~1024 px, searched with the same French keywords. Both are free with no key (Openverse anonymous quota: 20/min, 200/day). Measured on 2026-10-10, six spoken requests: the right picture each time, found and checked in 0.4–0.7 s.
  - « Une autre » calls the tool again with the same query; pictures already shown in the conversation are skipped, so the second one comes from Openverse. The whole search gives up after 8 s, as the voice device waits on it.
  - Screens are found, not configured: HA has no "has a display" attribute (a Nest Hub Max reports the same supported features as a Google Home speaker), so `ha_client` asks the template API for media players whose device model contains « Hub ». No screen, no tool. One screen per site, so the tool takes no room; a second screen would bring one.
  - Not downloaded by the server: nothing to store or clean up, no detour through the Paris relay (which only forwards `/tts/` and `/spotify/stream.mp3`), and the screen only needs internet access.

## 2026-10-10: Questions are not claimed actions

### AD-040: The empty-claim challenge skips questions

## 2026-10-10: Door locks

### AD-041: Lock by voice, never unlock
- **Context**: Paris added a Nuki Smart Lock Pro to HA (Matter, `lock.smart_lock_pro`, in no room); Charras has a Yale, « Porte d'entrée ». The server knew neither: `lock` was not a supported domain. Anyone within earshot of the Voice PE can talk to it, a radio or a TV included, and the server cannot tell voices apart (see the voice ID notes in ROADMAP).
- **Decision**: A `lock` tool, offered only where HA has a lock, and `get_state` reads its state. No unlock tool: its description tells the model to answer that unlocking takes the key or the app. « porte », « serrure » and « verrou » are generic names for the lock domain, so that « est-ce que la porte est verrouillée ? » reads the lock and not the alarm-sensor switches named « Bas Porte … » at Charras. A generic name of another domain resolves to nothing: « ferme la porte » sent as `close_cover` closes no shutter and sends no cover service to the lock.

Three locks now, from the outside in: the tool loop and the text fallback run only the tools offered this turn; `execute_function` refuses a name it does not know; `HAClient.call_service`, through which every HA write goes, refuses `lock.unlock` and `lock.open` whatever route led there.
  - The lock call is awaited, where other service calls are fired and forgotten (see the comment in `execute_function`): someone leaving the house on « porte verrouillée » must hear about it when HA could not reach the lock.
- **Measured** on gemma4:12b, 2026-10-10. The first description said « si on demande d'ouvrir ou de déverrouiller, réponds que… sans appeler de fonction ». The tool description now says to lock at every request, even a door locked earlier, and that no function opens or unlocks a door. Dropping that last sentence is worse: « déverrouille la porte » then called `lock` and answered « j'ai déverrouillé la porte », 3 out of 3. With both: 65/65 over 13 phrasings (lock, re-lock, state, unlock, open, a shutter), with and without history.
- **Trade-off**: Unlocking stays in the phone app. « Ferme la porte » means locking only when the model picks `lock`; the guard keeps it from moving a shutter instead.

### AD-044: An 8192-token context for gemma4:12b
- **Context**: Testing the two sites on 2026-10-11, every request at Charras came back empty. ## 2026-10-11: The web UI from a phone, without Tailscale

### AD-048: Through Funnel at /assistant/, behind a key link
- **Context**: The PWA (installable since 2fb5f6b) answered only on the tailnet (AD-042), over plain HTTP: installing it on a phone meant installing Tailscale there first, and even then Chrome offers no real install outside HTTPS. The other apps on charras (kiné, Par chœur, wiki) are public through Tailscale Funnel behind a link with a key, with nothing to install.
- **Decision**: Funnel publishes port 8888 at `https://charras-server.tailcef78d.ts.net/assistant/`; `web_ui.access_control` asks those requests for a key.
  - Funnel's proxy runs on this machine, so its requests come from loopback, which AD-042 trusted outright: published as it was, the UI would have handed the house to the internet. Apps on the same origin (wiki, kiné…) could send requests with the cookie; they are ours. `…/assistant` without its final slash loads the page with broken relative URLs: Funnel forwards both as `/`, so the server cannot redirect it.

## 2026-10-11: The music turned down while a request is heard

### AD-049: Every HA speaker playing at the site, from wake word to transcription
- **Context**: On 2026-10-11 at Paris, France Musique played on the Google Home next to the Voice PE; the requests that followed came out as « Est-ce que je peux mettre la boutique? », « La radio fille? », « What are you doing? ». ## 2026-10-11: The web UI knows which home the phone is in

### AD-050: Through Funnel, the home is the one whose internet connection the phone uses
- **Context**: The web UI's selector (AD-043) asks which home a typed command is for. From the phone, the answer is nearly always the home whose Wi-Fi it is on.

- **Context**: The children struggle with « Hey Jarvis ». ## 2026-10-11: What firmware 26.9.0 changed for the server

### AD-052: FLAC replies, VAD over the whole recording, follow-ups told by the reply
- **Context**: After the Voice PE's update from 25.6.0 to 26.9.0 (ESPHome 2025.6 → 2026.6, AD-051), wake words woke it, then a red LED. Four changes in ESPHome, each read in its source:
  - Audio comes in chunks of no fixed size, both mic channels together (« We don't target any particular message size »); 2025.6 sent 1024 bytes, one VAD frame. The VAD cut frames inside each chunk and dropped the rest: « No speech » on a recording where Silero, given whole frames, finds speech from 0.9 s.
  - The media player now decodes with micro-decoder, built with FLAC and MP3 only: « Could not determine audio file type from URL or Content-Type » on every WAV reply. No playback within 2 s, and the firmware reports the announcement finished anyway.
  - An announcement that fails stays first in the announcement queue: a later one is played only when nothing is queued before it, so every reply after the first failure was queued, unplayed (no GET for 33 of 34 announcements).
  - The follow-up's START carries the last wake word again (2025.6 cleared it), so `wake_word_phrase is None` no longer tells a follow-up: each one was taken for a new conversation, without the 500 ms echo skip.
- **Decision**: The VAD reads the recording from an offset, so a frame may span chunks. Replies are written as 48 kHz mono FLAC by ffmpeg (~35 ms; already a dependency for Spotify), the satellite's announcement format: at 16 kHz it ran a resampler beside three wake word models (its stop word joins during replies) and a reply stuttered, their length read from STREAMINFO for the announcement timeout. Each reply first sends STOP to the satellite's announcement queue, which empties it (a STOP and an announcement right after: the announcement plays). A START within 3 s of a reply that asked for a follow-up is the follow-up.
- **Trade-off**: A wake word said within 3 s of a follow-up reply counts as the follow-up; the satellite is listening then anyway. The STOP would cut one of the satellite's own sounds still playing at reply time. The Spotify stream was MP3 already.

- **Context**: Transcription failed at 07:12, 08:12–08:13 and 14:15–14:16 with `CUBLAS failure 3: the resource allocation failed` on `cublasCreate` (`cuda_execution_provider.cc:231`, the CUDA handles ONNX Runtime makes the first time a thread runs a session: STT and TTS ran on asyncio's default pool, shared with DNS lookups and the calendar, so a request could land on a thread new to the encoder). The 16 GB card was full each time:
  - In the morning, a third process, maratrail-live's (2656 MiB), sat beside Ollama (8572) and the voice server (4582 freshly started): 15830–15844 of 16311 MiB, 7 MiB free at 07:40. The 08:12 failure was the first request after a restart. The restarts at 08:17 and 08:21 failed to create their CUDA sessions, and ONNX Runtime fell back to the CPU for STT and TTS, with a log line only, until 10:08.
  - In the afternoon, with no third process, the voice server had grown from 4.6 to 7.2 GB in six minutes of conversation, a 30 s recording among them: 15825 of 16311 MiB.
  - What grows, measured in a standalone process with the service stopped and Ollama resident, over 32 recordings of 1 to 30 s and replies of 4 to 80 words: each session's arena (BFC), which ONNX Runtime extends to fit each new input length and never shrinks. With the default `kNextPowerOfTwo` the extensions double (+1024 MiB at once on one reply): 4586 MiB loaded, 6692 MiB after the requests, 7248 MiB in another run (production after the failures: 7238). Requests on 8 new threads: no visible growth. cuDNN's algorithm search (`HEURISTIC`, `cudnn_conv_use_max_workspace=0`): no change. `kSameAsRequested` alone: 3746 MiB loaded (the weights, allocated in the arena, had been rounded up to powers of two), but the fragmented arena grows back to 6672 MiB.
- **Decision**: `onnx_gpu.py`, used by `stt.py` and `tts.py`:
  - every STT and TTS run on one thread (`ThreadPoolExecutor(1)`): two runs never add up their memory, and the CUDA handles are made once;
  - arenas extended by what a run asks (`kSameAsRequested`), weights outside them (`session.use_device_allocator_for_initializers`);
  - for Kokoro and Parakeet's encoder, whose activations follow the length, the arena shrinks at the end of each run (`memory.enable_memory_arena_shrinkage`). onnx-asr takes no run options, so its encoder session's `run` gets them after loading (`model.asr._encoder`, onnx-asr pinned at 0.11.0). Not the TDT decoder: it runs once per audio frame, shrinking it too cost 32 ms per transcription (0.150 against 0.118 s), and its arena does not grow.
- **Measured**: same requests, then 60 + 12 more: 3748 MiB loaded, 4232 MiB after the first requests, then flat; 4949 MiB at most during a run (NVML sampled every millisecond; 6697 before). The card at most 13.5 of 16.3 GB with Ollama, against 15.8. STT 0.118 s on average before and after; TTS 0.355 s before, 0.341–0.368 s after over three runs, within run-to-run noise.
- **Trade-off**: Each run of Kokoro or the encoder allocates its activations again; the timings above include it. The STT and TTS of two requests wait for each other (there is one conversation at a time anyway). A third GPU process still does not fit: with maratrail-live's 2.7 GB, a run's peak would take the card to 16.2 of 16.3 GB. The CPU fallback at startup was still silent beyond its log line, until AD-055.

### AD-054: One announcement per reply

### AD-055: STT and TTS on the CPU when CUDA fails, back on CUDA once it works
- **Context**: On 2026-10-11, the restarts at 08:17 and 08:21 UTC found the card full (maratrail-live beside Ollama, AD-053). ONNX Runtime 1.27's Python `InferenceSession` caught `CUDA failure 100: no CUDA-capable device is detected` (`cudaSetDevice`) and created each session again on the CPU, printing an `EP Error` banner. STT and TTS ran on the CPU until a restart at 10:08, with nothing but `Kokoro providers: ['CPUExecutionProvider']` to say so; nothing reads `/health`. Reproduced by filling the card from another process: with 10 MiB left, the same error at the same line. With 2 GB left, room for a CUDA context but not Parakeet's weights, the error is ONNX Runtime's `Fail` at `cudaMalloc`, which its fallback does not catch (not a `RuntimeError`): the server stopped at startup (`Fatal error`), and systemd restarted it every 5 s.
- **Measured**: the same 7 requests (2–9 s, spoken by Kokoro, plus 1 s of silence) and 7 replies (2–43 words, 0.7–14.5 s of speech), median of 3 runs each, service stopped, Ollama resident:

  | | GPU (RTX 5060 Ti) | CPU (i5-14400F) |
  |---|---|---|
  | STT | 0.03–0.14 s, 0.084 s on average | 0.27–0.65 s, 0.43 s on average (5×) |
  | TTS | 0.03–0.27 s, 0.018 × real time | 0.37–2.5 s, 0.17 × real time (10×) |

  On the CPU, a request is heard 0.1–0.6 s later and answered 0.3–2.2 s later: slower, but the house keeps its assistant.
- **Decision**: `onnx_gpu.load` and `onnx_gpu.retry`, used by `stt.py` and `tts.py`:
  - sessions created without ONNX Runtime's fallback (`enable_fallback=0`). A model is on CUDA once built and run once; when either fails, with any exception, it loads on the CPU and an ERROR names CUDA's error. Loading happens on the models' thread, where the test run makes its CUDA handles;
  - `/health` gives each model's `device`; `status` is `degraded` while one runs on the CPU though onnxruntime has CUDA (`onnx_gpu.lost_cuda`), still with 200 since it works;
  - while one does, the server tries CUDA again every minute, between requests, in the same process (`_back_to_gpu`), and swaps the model once it works. A failed attempt takes 0.1 s (no room for a context) to 0.9 s (no room for the weights) and keeps no GPU memory; a successful one 1.4 s for Parakeet, 0.5 s for Kokoro. The test run matters there: on the thread where CUDA had failed, the first run after the card was freed failed too, once, with a stale `cudaErrorMemoryAllocation` in Parakeet's first node, then worked. That attempt fails, the next one succeeds;
  - a session's `run` patched for arena shrinkage (AD-053) holds its session through a weak proxy: bound in the partial, the session held itself, and a model dropped after a failed attempt stayed on the card, 2.4 GB for Parakeet, until the garbage collector's next pass;
  - onnx-asr's resampler, never used (we pass 16 kHz), on the CPU: it made seven CUDA sessions.
- **Rejected**: failing startup so that systemd retries: no assistant at all for as long as the card stays full, when the CPU answers a second later. A log line or `/health` alone: nothing watches them, and the slowness would last until the next restart. A restart once the card has room, rather than a reload: CUDA does work again in the same process, and a restart would cut timers and music.
- **Trade-off**: An attempt holds the models' thread up to 1.5 s; none starts while a voice request is recorded or answered, but one arriving meanwhile waits for it. Without ONNX Runtime's fallback, a run failing with `EPFail` raises for its request, where the session moved to the CPU for good, unsaid.

## 2026-10-11: Pages of other sites kept off the API

### AD-056: POSTs take JSON only, and the Host must name this server
- **Context**: AD-042 opens the API to localhost and the tailnet by the client's address, and a browser on a tailnet device is such a client whatever page it shows. On the live server on 2026-10-11, `/api/dry-run` ran a request sent as `text/plain` (`read_text` parsed any body as JSON, else took it whole as the prompt), and `/api/exchanges` answered 200 to `Host: evil.example`. Two ways in for a page of any site:
  - a form, or a `fetch` with a `text/plain` body, crosses sites without the browser asking the server first (no CORS preflight): a POST to `http://100.72.204.126:8888/api/send` ran its command, unseen by the page;
  - DNS rebinding: the page's own name, once the page is loaded, pointed at 100.72.204.126 (or 127.0.0.1 on charras) makes it same-origin with the server: it reads transcripts and sends JSON. Its requests still carry its name in `Host`.

  Through Funnel, the cookie's SameSite=Lax already kept other sites out (AD-048); nothing did on the tailnet.
- **Decision**: `web_ui.cross_site_guard`, a middleware before `access_control`:
  - A request other than GET or HEAD needs `Content-Type: application/json`, else 415. Cross-site, a JSON POST makes the browser send an OPTIONS preflight first; no route answers it, and the POST is never sent. `read_text` lost its text fallback; a body that is not JSON gets 400. `test_e2e`'s reset sends `{}`, and the startup log's example uses `curl --json` on localhost (it named the LAN address, refused since AD-042).
  - The Host must be an IP address, `localhost`, the machine's name (`charras-server`, MagicDNS's short name) or a name under `ts.net`, else 421; a request without one passes, browsers always send it. Rebinding needs a name whose DNS the attacker answers: an IP address cannot be rebound, and Tailscale answers for `ts.net`, MagicDNS names inside the tailnet and Funnel's in public DNS. Funnel forwards the visitor's Host (`charras-server.tailcef78d.ts.net`, seen on loopback with tcpdump).
  - The speakers' paths (`/tts/`, `/spotify/`) skip both: speakers and the Paris relay are no browsers, and no Host they send should cut a reply or the music. `/health`, which the LAN may also fetch, does not: it names the satellites and the LLM, and its callers use localhost. A rebound page could fetch a reply's audio only by its name, the time and a hash of its text.
- **Measured** on the live server after c99e589: `Host: evil.example` 421 on `/api/exchanges` and `/health`; `localhost`, `charras-server`, 100.72.204.126 200; `text/plain` and form POSTs 415, `curl --json` 200 (dry run, reset); the Spotify stream 200 under a foreign Host. Through Funnel: manifest 200, API 401 without the cookie, with it a JSON dry run 200 and a `text/plain` one 415.
- **Rejected**: checking `Origin`: browsers leave it out of same-origin GETs, which is how a rebound page reads transcripts, and a POST from a browser that omits it would pass, where a JSON body fails closed. A CSRF token: the UI and `test_e2e` would carry it for what JSON already gives.
- **Trade-off**: Another name for the server (`.lan`, `.local`, a domain of ours) gets 421 until added to `_OUR_NAMES`. `curl -d` against the API needs `--json` now. Another tailnet's `ts.net` names pass the check; Tailscale, not the attacker, answers for them.

### AD-057: Spotify results ranked on the request's words, number and key; the music's title on the screen
- **Context**: Paris, 2026-10-11, three requests in a row for Bach's second prelude, the C minor one (BWV 847): `play_music` got « Prélude numéro 2 de Bach », then « … (version classique) », then « … en Do mineur (C minor) », and played Maurane's « Sur un prélude de Bach », then the prelude in C major (BWV 846) twice. `find` took Spotify's first result, or the first whose name was the query: Spotify ranks by popularity more than by the words, and the C minor prelude was not even among the ten results of the last query as said; it was among those of « prelude 2 bach c minor ». The Web API now gives at most 10 results per search (400 above). The Nest Hub playing the stream showed « Default Media Receiver » and « Live »: `play_media` sent a URL and nothing else.
- **Decision**:
  - `spotify.best_match` ranks the results again: one point per word of the request found in the title, album or artists (words of five letters or more match on their first five, so « symphonie » finds « Symphony »), a point for the request's key, one off for another key. Keys are read in French, English or German (« do mineur », « C minor », « c-Moll »). Filler words (articles, « numéro », « version », « classique ») count for nothing. Among equals, Spotify's order; an exact name no longer comes first: « Get Lucky » was L.E.J's cover, « Sonate au clair de lune Beethoven » a nursery version so titled.
  - A request with a number or a key is also searched as the catalog writes it (`search_variant`: « prelude 2 bach c minor »), at the same time; the two lists are ranked together. Measured on 18 requests (classical, French and English songs, albums, artists, playlists): the three Bach requests now find BWV 847, « Get Lucky » Daft Punk; the others are unchanged.
  - A screen (`ha_client.screens`) gets Cast's music metadata with the stream, through HA's `play_media` `extra.metadata`: title, artists, album and cover of what was asked (the track, the album, the artist's or the playlist's picture), or of the track playing when the music moves there. A screen already on the stream loads it again for new music, so that it shows it; music starts once it has joined, as before (AD-037). Checked on the Paris Nest Hub: HA then reports `media_title`, `media_artist`, `media_album_name` and the cover as `entity_picture`.
- **Rejected**: letting the LLM choose among the results: one more round (~2–3 s) and a 12B model's choice. Sending the metadata to every HA speaker: the Sonos has no screen, and its handling of `extra` was not checked.
- **Trade-off**: The screen keeps the title it was given: when the track changes (an album, a playlist, or the radio Spotify goes on with after a single track), the Default Media Receiver can only show new metadata by loading the stream again, an audible cut at each track. New music on a screen waits for it to reconnect (~1.5 s) before it starts. A request with a number or a key costs two searches.

## 2026-10-13: The phone as a second satellite

### AD-059: The web app listens through the phone's microphone, the server's VAD hears the end, the phone speaks the reply
- **Context**: Paris has one Voice PE, on the kitchen island. The web app, installed on a phone since AD-048, was already used as a remote: 8 typed requests from a phone between 2026-10-11 and 10-13 (shutters of the children's rooms in the morning, lights at night, an appointment in the calendar). Its page was still AD-022's debug log: every exchange with its timings, a « Debug » button each, the reply's audio behind a button, timers and music nowhere.
- **Decision**: the page is rewritten as a voice assistant, a satellite in the pocket.
  - A tap on the microphone (or the launcher's « Parler » shortcut, `?parler`) streams the microphone to `/api/listen`, a WebSocket: 16 kHz 16-bit mono in 64 ms binary messages, downsampled in an AudioWorklet. The server runs the satellite's VAD on it (`vad.SpeechEnd`, shared with the Voice PE's path), with its limits: 8 s for speech to start, 5 s after a reply, 30 s in all; a tap on the orb ends it sooner. Then STT, LLM and TTS (`answer_recording`, beside the satellite's pipeline); the page gets `speech`, `heard`, `transcript` (shown at once, before the LLM answers), then `reply` with the reply's audio, which the phone plays. Unless the reply said goodbye or started music, the phone listens again, 5 s, as the Voice PE does. The request is recorded and logged as `app`; closing the page while it is being answered does not stop it.
  - The browser's noise suppression is off (`noiseSuppression: false`), its echo cancellation and gain control on: on « Quelle heure est-il ? » spoken by Kokoro into Chromium's fake microphone, WebRTC's suppression gave « Quelle mort est-il ? » in 3 of 4 runs with everything on, 2 of 3 with the gain control off, and the right words in 6 of 6 without it. The AudioWorklet's box filter gives the same transcripts as ffmpeg's resampler on three requests.
  - `cross_site_guard` checks the `Origin` of WebSocket handshakes: browsers open WebSockets across sites without a preflight, and AD-056's JSON rule does not apply to them, so a page of any site, open in a browser on the tailnet, could have streamed a spoken command. Browsers always send Origin on a handshake; its host must be the request's. Through Funnel, the cookie's SameSite=Lax already kept other sites out.
  - Typed requests (`/api/send`) get no TTS: their reply is read. A goodbye now ends the conversation whatever heard it: `end_conversation` marks it expired, and the next request starts a new one, where the satellite used to clear it after its reply.
  - What runs now (`/api/state`): the home's timers, counting down, with ✕ (`/api/timers/cancel`, which also stops the satellite's countdown; an id now cancels that timer only, the « only timer running » fallback being for spoken requests); Spotify's track, cover and speaker, with pause and next (`/api/music`, through `music_control`).
  - The log becomes a conversation: requests on the right (the Voice PE's in a paler blue), replies on the left, one chip per tool call naming what was done, in orange when the result says nothing was (« non trouvé », « hors ligne », « Rien n'a été fait »…: the server flags such calls `failed` in the log), so that a reply claiming otherwise shows. Timings, calls with their results, the recordings and the satellite's false wakes are behind « Détails techniques » in the settings, which also show `/health`.
  - Shortcuts: what this phone asked at least twice, ranked by recency and by closeness to the time of day (the shutters at 7:00, the lights at 23:00), one tap to send again. Requests are grouped by what they did, their tool calls and arguments with accents, articles and plurals aside, so that « Ouvre les volets chez Zoé » and « Ouvre le volet de la chambre de Zoé » count as one; none that failed or only said goodbye. The wording sent is the most used, else the one naming most of the arguments: « tu peux l'éteindre » needed its conversation. Kept in the browser only.
  - The page polls every 3 s while shown and not at all hidden; `/api/exchanges` answers 304 when unchanged.
- **Measured** on a test instance of the server (port 8899, CPU only, no satellite, no Spotify), Kokoro's « Quelle heure est-il ? » streamed in real time: speech heard at 1.3 s, end of speech at 3.2 s (the second of silence), transcript at 3.6 s, reply at 6.9 s (STT 0.41 s and TTS 0.53 s on the CPU, LLM 2.7 s). Headless Chromium with that file as its microphone: listening, speech, thinking, the reply played, follow-up listening, in a loop; a timer started by voice appears in the strip and goes away with its ✕; cancelling while listening logs nothing. Silent: `heard` after 8.0 s (5.0 s as a follow-up), « [Rien compris] » logged only for the first. A handshake with `Origin: https://evil.example` gets 403.
- **Rejected**: the browser's speech recognition (Web Speech API): Chrome sends the audio to Google, Firefox has none, and the request would not be Parakeet's nor kept with the others. Detecting the end of speech in the page (an energy threshold, or Silero in onnxruntime-web, megabytes to load): the server's is the satellite's, already tuned. MediaRecorder's Opus decoded by ffmpeg: a decoder per request for a stream of 32 kB/s, which mobile data carries. Pushing the log to the page (Server-Sent Events): polling with ETags costs a 304 every 3 s.
- **Trade-off**: The microphone needs HTTPS: through Funnel, not over the tailnet's plain HTTP, where the page can only type. No wake word: a tap, or the launcher's shortcut (on Android, Chrome lets an installed app start its audio without a tap; elsewhere the shortcut asks for one). Timers still ring at the satellite only (until AD-070). The phone has no room: « éteins la lumière » is no more precise from it. The page sends its home with every request, picked once by its Wi-Fi when shown (AD-050), so a phone leaving home keeps it until it is shown again. The Origin check lets the other apps of charras-server's Funnel name through, as the cookie does (AD-048).

### AD-060: The app shows its own conversation; the history is a screen of its own

### AD-061: Each device its own conversation
- **Context**: A site had one conversation, shared by whatever spoke to it. A phone request a minute after the children's riddles at the kitchen's Voice PE was read in their context, and the phone's screen, showing its own requests since AD-060, did not show that context: the model and the screen disagreed on what the conversation was. ### AD-070: A timer set from the web app rings on the phone that set it; on the satellite unless that phone is away
- **Context**: A timer rang only on its home's satellite (AD-059's trade-off). Set from the phone, « mets un minuteur de 10 minutes » rang in the kitchen. Headless Chromium (Playwright's build, persistent profile) on a test instance (port 8899, the real routes and `Push`, the rest stubbed): it subscribed through FCM. With the page shown, the toast came at 0 and the notification a second later, silent; with the app closed, it stayed until dismissed and vibrated. A reload kept the subscription. The bell appeared on this phone's card only, in light and dark. Headless Firefox got no subscription from Mozilla's service, and no real phone was tried.
- **Rejected**: pywebpush, which is synchronous (requests) and brings py-vapid and http-ece, for ~60 lines over `cryptography`, already installed with aioesphomeapi. Every phone of the home told of every timer: the satellite is there for those at home. The satellite ringing for a phone away: an empty house, or the family disturbed.

A phone on Tailscale reaches the server over the tailnet, not Funnel: it is never away, so the satellite rings its timers. A phone offline for more than 10 minutes when the timer ends never hears of it. The notification makes the phone's notification sound, not an alarm, and the page's chime stays silent until a tap. The push services see when a message goes and its size, not what it says.

- **Context**: 2026-10-24 at Charras, Ivan tested the new combles shutter (`cover.velux_external_cover_roller_shutter_10`, two floors above the Velux gateway). « Ferme le volet des combles » worked. « Tu peux le rouvrir », 13 s later, was called and acknowledged by HA, but the shutter never got it: the gateway lost it (home-infra `charras/NETWORK.md`). Ivan then said « il continue de se fermer, et il ne se rouvre pas ». gemma4:12b answered « Je suis désolé, je vais essayer de le rouvrir à nouveau pour toi. », with **no function call**. The AD-040 challenge did not fire: `_ACTION_CLAIM` knew « je ferme / j'ai fermé » but not a promise (« je vais … rouvrir »), nor the re- forms (« je rouvre », « j'ai refermé », « je relance »). A third request was needed.
- **Decision**: `_ACTION_CLAIM` takes every verb with its re- prefix (`re`/`r`: rouvre, referme, rallume, remets, relance), in the past and the present, and adds « je vais [essayer/tenter de] [le/la/les/l'…] <infinitive> » and « je m'en occupe ». A typographic apostrophe is folded to `'` first, as the model sometimes writes « c’est fait ». The challenge text says « annoncer une action, faite ou à faire » rather than « affirmer avoir effectué », which fit a promise badly. Questions stay out (AD-040); « je ne vais pas ouvrir », « le volet va se rouvrir » and « je vais vérifier » do not match.
- **Measured**: replayed on the 235 replies of the recordings and the exchange log (116 with no call): 0 that matched before and no longer does; 2 new matches, both from this morning: the reply above (no call: the case to catch) and « Je relance l'ouverture du volet des combles. » (which came with its call, so is never challenged).
- **Then, live**: deployed, and the morning's three turns replayed 4 times by dry run (`/api/dry-run`, site charras, conversation reset each time). Once the model gave the morning's reply, was challenged, and called `open_cover`. Three times it said « Je suis désolé, je vais essayer de forcer l'ouverture du volet des combles à nouveau. », which the first version missed: no listed verb, the order named as a noun. So any promised attempt (« je vais essayer/tenter/réessayer d… », « je réessaie ») now counts, and so does a verb followed by « l'ouverture », « la fermeture », « l'ordre » or « la commande » (« je relance l'ouverture », « je viens de renvoyer l'ordre »). « Je vais vérifier » still does not: a narrower call, left for when it shows up. Same replay result over the 235 replies (in them, « je vais » only appears in the morning's reply).
- **Measured after aeab11c**: the same 4 dry-run replays: 4 out of 4 challenged (3 times « je vais essayer de le rouvrir », once « …forcer l'ouverture… ») and then `open_cover`, answered « Je relance l'ouverture du volet des combles. ». No challenge on « Le volet des combles est ouvert ? » (`get_state`), « Quel temps fait-il demain ? » (`get_weather`), « Merci, bonne journée. » or « Tu vas bien ? » (« Je vais très bien, merci ! »). **Correction (2026-10-25)**: « Merci, bonne journée. » was not challenged, but it was not fine either: it came back **empty after 67 s**, gemma4 hitting `finish_reason=length` with no text at 500, 1000 and 2000 tokens. This entry first listed it as passing; the 2026-10-25 nightly review caught it. Unrelated to the claim check, and open.
- **The shutter's side, for the record**: the lost « rouvre-le » was not the Velux ignoring a reverse order. Tested the same morning through HA (home-infra `charras/NETWORK.md`, b2b3a7b): an `open_cover` sent 9 s into a close stopped and reversed both the couloir shutter (_4, at 71 %) and the combles one (_10, at 60 %). Not done.
- **Trade-off**: A wider net means more chances to challenge a reply that needed no call; the replay found none, and the challenge's own text tells the model to answer without claiming to act when nothing is to be done.

- **Context**: On 2026-10-30, « Prélude numéro 2 de Bach » found « Bach, JS: Well-Tempered Clavier, Book 2, Prelude and Fugue No. 23 in B Major, BWV 892: I. Prelude » by Piotr Anderszewski. They were not: only playlists are looked up in the library first (AD-037), and go-librespot cannot list the liked tracks, only tell whether given ones are (`/library/liked?uris=`, 22 ms).
- **Decision**:
  - A number asked after « numéro », « n° » or « No. » counts only against the result's own number: the one its title tells so (« No. 23 », « n°2 », « Op. 9 No. 2 »), else any but a book's, volume's, disc's, opus's or catalogue's (« Gymnopédie 1 », « 5ème symphonie »; not « Book 2 », « BWV 892 », « K. 545 »). A number asked bare (« Les 4 saisons ») is a word like the others, as before.

  - Among results of the same score, a track the account liked wins, then Spotify's order. go-librespot is asked about the results (half a second at most; when it cannot tell, none is taken as liked).
  - The words before a piece's number (`_NUMBER_MARKERS`) are listed once, for the filler, the number said in words and the number told: « No. deux » now reads as 2 too.
- **Measured** on 2026-10-30, `Spotify.find` before and after on the live search, 12 requests for a numbered classical piece: the piece of that number by that composer 9 times before, 12 after. The composer first in place of `search_variant`, for two searches instead of three: the variant found more of « Nocturne numéro 2 de Chopin » and « Sonate numéro 14 de Beethoven ». An `artist` argument to play_music, which would name the composer without reading « de »: a tool change for the model to learn. Asking go-librespot only when the best results tie: 22 ms saved for a second code path. A liked track before any other, as playlists are: it can only be found among the search's results, and a better match is what was asked.
- **Trade-off**: A third Web API search for a numbered or keyed piece, in parallel. « de … » is read as the composer even when it is not (« Sonate au clair de lune numéro 14 » searches « lune 14 sonate clair » as well). A catalogue number told alone (« Prelude in C Minor, BWV 847 ») still does not count as « numéro 2 »: the ranking knows no catalogue. ### AD-091: The Spotify stream is read 10 s ahead of the speakers, which get it at once; the track heard is told
- **Context**: On 2026-10-29 at Charras, the living room's Google Home took a long time to play the music asked; Ivan told his coach. Its Wi-Fi was not at fault (a UniFi access point in the room, on Ethernet). On the night of 2026-10-30, a test server sent beeps at the stream's bitrate to that Google Home, at 3 % volume, its states read from HA. Sent at real-time pace, as `/spotify/stream.mp3` was: it played about 1 s, stalled, and played again at 22.7 s, once it held about 22 s of audio, 6 starts of 6; loaded again while playing, still buffering after 12 s, 5 of 5. With 3 s sent at once: no stall 5 times of 9 from cold, 0 of 5 loaded again. With 6 s: played 1.5 s after the command without a stall, 3 of 3 from cold, and 1.7 s, 3 of 3 loaded again; 10 s and 22 s, 6 of 6 each way. So past its stall the Google Home held a 21 s reserve: what it played was 21 s behind go-librespot, whose state the model is told, and « pause » or « suivant », told go-librespot alone, were heard 20 s late. A silence sent first gave the head start without the reserve problem, at the cost of seconds of silence before every music: Ivan refused it.
- **Decision**:
  - The stream reads go-librespot's FIFO 10 s ahead of what the speakers play: its clock is the audio encoded (`position`), the speakers play `heard`, 10 s behind, and the MP3 in between is kept. A speaker that joins gets it at once, then the stream at real-time pace. go-librespot writes as fast as the FIFO is read, so the 10 s are the music's own; nothing waits. The FIFO holds 0.37 s, which go-librespot refills at once: while the head start is read, the stream reads it every 5 ms rather than every 50, and a speaker is loaded once it is read (`head_start`, 2 s at most).
  - New music, next, previous and resume go to go-librespot first: the stream drops what it read of the old music (`switch`) and starts again (`restart`) at go-librespot's event that shows the change (its `/events` websocket: `metadata` for a track loaded, `seek`, `playing`). `heard` then waits at the music's start until its speaker joins, the head start read meanwhile, so that it is heard from its start. Its speaker is loaded again even if it already plays the stream (`_point_at_spotify(reload=True)`): it would play the old music it holds first. Music no longer waits for its speaker before go-librespot plays it (AD-037, AD-057): a speaker that never joins has go-librespot paused again.
  - Pause pauses go-librespot and its speaker, which stops at once instead of playing out its reserve, and takes go-librespot back to where the speakers were: resumed from here or from the phone, it starts there.
  - The track heard: go-librespot's events mark where each track starts on the stream (`_Mark`), from which `Spotify` tells the track at `heard`: in the last 10 s of a track, the one ending, not go-librespot's next. The model's context message, `music_control current`, the app's card and a screen's metadata say it. Next, previous and pause are go-librespot's steps from its track to the one heard (`_steps`): « suivant » during those 10 s starts go-librespot's track from its start rather than skip it; « précédent » follows Spotify's rule (past 3 s, the same track again; before, the one before) on the track heard, go-librespot's own seeing a position 10 s further.
  - When go-librespot sends nothing (paused from the phone, a track slow to come), silence keeps the speakers 2 s ahead, rather than a tick at a time. The stream keeps where it added silence, which is no track's time.
  - Without go-librespot's events (it restarted, or answers no websocket), go-librespot's own track is told and its own next/previous run, as before.
- **Measured** on 2026-10-31 at 10:40, the living room's Google Home at 3 %, the real stream (Gould's prelude, then what followed it), states read from HA, timed from the request (`/api/redo` for play_music, `/api/music` for the controls): played 2.05 s after play_music from off; next 1.43, 1.13 and 1.12 s; previous 0.82, 0.92 and 0.92 s; paused 0.1 s after pause, twice; resume 0.72 and 0.82 s. No stall in the 15 s after each; every join got 10.1 to 10.3 s at once. A first version read the head start at a 50 ms tick and loaded the speaker without waiting for it: it joined 0.15 s later with 1.1 to 1.3 s, and previous stalled 12.7 s.
- **Rejected**: Silence before every music, to give the head start (Ivan: « ça me paraît bizarre qu'on se retrouve obligé de se mettre 3 secondes incompressibles de délai »). go-librespot's own position, which `/status` derives from the wall clock since a track's load: after a head start read in half a second, it is 10 s behind its decoder. Polling `/status` for track changes: same, and late. A head start of 6 s, enough in every test: 3 runs each way only, and 10 s gives a margin. A unique URL at each load, in case the Cast ignored a load of the same URL: it loaded the same URL again each of 11 times. A bigger FIFO (`F_SETPIPE_SZ`), for a faster head start: it would hold more of the old music at a change. A head start per speaker, the satellite needing none: not measured to matter.
- **Trade-off**: go-librespot is 10 s ahead of the speakers, or more after waiting for a speaker: what it plays, its Spotify Connect state on the phone, is that far ahead. A change of music drops what was read of the old one but not what go-librespot had already written in the FIFO, up to 0.4 s of it, as before. A speaker that joins gets 240 KB at once: the Voice PE, the Sonos and the Paris relay were not tried with it. Next, previous and resume load the speaker again, a second without sound, the satellite too. Paused from here, the speaker is paused: resumed from the phone's Spotify, go-librespot plays to nobody, and pauses after 5 s.

## 2026-11-20: The satellite's microphone stuck low

### AD-113: Speech too quiet for the VAD after a wake word is a request after all, and the satellite restarts
- **Context**: Paris, 2026-11-20 at 12:53 and 12:54: two requests after « Okay Nabu », 8 s each, got the red LED, the VAD having heard nothing (AD-036). Their level (the 90th percentile of their half-seconds' RMS, the first left out) was 54 and 88. Since 2026-10-11, every wake-word request the VAD heard was at 431 or more, the room after a false wake at 345 or more. Their noise floor was 18 and 20, against 84 or more on every other wake-word recording. The wake sound, which the satellite's own microphone hears, was at 3,500, against 11,000 to 27,000 on 2026-11-18. Silero scored them 0.27 and 0.41 at most, and 0.89 and 0.99 amplified ×10. Parakeet wrote them right as they were: « Tu peux fermer la porte de la porte? » and « Tu peux fermer la porte de l'appart. ». The satellite restarted through its Restart button at 12:58, and the next request came back at 473, its wake sound at 27,155, the follow-up at 2,738. That morning the Paris link had dropped three times (6:53, 10:18, 10:32), Home Assistant and the satellite together.
  - The wake word kept working because it listens to channel 1 of the Voice PE's XMOS chip, ×4 on the ESP, and microWakeWord's front end evens out the level. The request is channel 0, which goes through echo cancelling, interference cancelling, noise suppression and automatic gain (esphome/voice-kit-xmos-firmware#10). The satellite sends both (`data2`, `home-assistant-voice.yaml` 26.9.0); the server dropped the second.
  - No firmware fixes it. 26.9.0 is the latest stable release; the 26.11.0 pre-release says nothing of the microphones; the XMOS firmware (1.3.1) has not changed since 2024-09; no issue of the Voice PE's or the XMOS firmware's tells of this.
- **Decision**:
  - After a wake word, a recording the VAD found silent goes through a fresh VAD a second time, amplified ×10, when its level is under 200 (`vad.quiet_speech`, 40 ms, in a thread). If speech is found there, it is a request: thinking LED, Parakeet on the recording as it is, an answer. Its JSON has `quiet_mic`, its level, and the journal a WARNING. Not in a follow-up, which ends quietly as before.
  - The satellite then restarts through its Restart button once idle (no reply, music or recording, no follow-up awaited), at most once an hour (`_restart_satellite`).
  - Channel 1 is kept beside each satellite recording, as `….ch1.wav`: what it does when channel 0 sticks is unknown. The review does not copy it, and the app does not play it.
- **Measured**: the 200 wake-word recordings of 2026-10-11 to 2026-11-20 replayed through `SpeechEnd` and `quiet_speech`: 4 silent. Today's two are requests (54, 88). The room after a false wake (345) is not, nor « Oh » (AD-092's burst, at 5,625).
- **Rejected**: the wake sound's level as a gauge: from 118 to 27,000 among requests answered well (the satellite's volume, the echo canceller). Amplifying every recording before the VAD: the room after a false wake (345 to 2,032) would become requests (AD-036). Restarting the satellite on a schedule: music cut, for a fault seen once. Channel 1 for the request: nothing yet says it stays sound when channel 0 does not.
- **Trade-off**: the threshold rests on one satellite's two failures. A request between 200 and 430 that the VAD misses still gets the red LED. A false wake in a quiet room whose noise the amplified VAD takes for speech becomes a request, and restarts the satellite. A rescued request waits the whole 8 s: the VAD never hears it end. A restart loses a timer's countdown on the ring, which still rings (ESPHome takes a FINISHED for a timer it does not know).
